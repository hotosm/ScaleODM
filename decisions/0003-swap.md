# Swap-based Memory Sizing for ODM Jobs

## Context and Problem Statement

ScaleODM sizes each ODM `process` pod from the image count, using a fitted table
in `app/workflows/standard.go`. That table predicts the **peak** working set: a
brief spike (notably `mvs-texturing`) that lasts seconds to minutes, not the
steady-state resident set.

Previously the pod requested the whole peak as real RAM (request ~= limit,
Guaranteed QoS). This over-provisioned nodes badly. Field data:

- 3000 images peaked at ~144Gi but ran fine on a 62Gi RAM + 127Gi swap host.
- 5000 images ran on ~62Gi RAM + swap, versus a ~227Gi estimated peak.

Provisioning the full peak as RAM means paying for 3-4x the RAM actually resident
for all but a few seconds of the job.

## Considered Options

- **Request the full peak as RAM** (status quo). Simple and safe, but wastes
  large amounts of RAM and caps how many images a given machine can process.
- **Request steady-state RAM, absorb the peak with swap.** Request a fraction of
  the peak and let the kernel spill the brief spike to disk swap under
  Kubernetes' `LimitedSwap` policy.
- **Lower the estimates outright.** Rejected: the peak is real and would OOM-kill
  without swap to catch it.

## Decision Outcome

We request the steady-state RAM and back the peak with swap:

```
request (real RAM)   = peak / (1 + SWAP_RATIO)          # prod ratio 1.0, so ~1/2 of peak
limit   (OOM ceiling) = peak * (1 + MARGIN_PERCENT/100)  # backed by RAM + swap
```

Because `request < limit`, every process pod is Burstable QoS and the kernel
grants it swap. Nodes are configured with swap (AWS via the Karpenter
EC2NodeClass, other clusters via a disk swapfile). This is the design that lets
5000 images request ~114Gi RAM (peak 227 / 2) + swap instead of a ~227Gi RAM
node. (Prod originally ran the more aggressive `2.0` - request = peak/3 - but a
node-pressure eviction showed the resident set can exceed a third of the peak;
see the amendment under "Headroom and OOM risk".)

### How it works

Swap is split into two independent layers so the same build runs anywhere:

- **Node layer:** swap exists on the node and kubelet allows it
  (`failSwapOn: false`, `NodeSwap` feature gate, `swapBehavior: LimitedSwap`).
  Provisioned per-platform.
- **Workload layer:** the pod declares `request < limit`. Platform-agnostic;
  ScaleODM never needs to know how a node got its swap.

Each workflow is annotated with `scaleodm.hotosm.org/burst-headroom-gib`
(`limit - request`) so operators can confirm nodes carry enough swap.

Setup and tuning knobs are in [`docs/swap.md`](../docs/swap.md).

## Headroom and OOM risk

There are three buffers against an outlier job OOM-killing, in order of how much
they actually contribute:

1. **Swap = 2x node RAM.** Total addressable capacity is `RAM + 2*RAM = 3*RAM`,
   which matches `request = peak/3`, so a node sized to the request holds the
   whole peak. Swap is on NVMe instance store, so paging into it is fast.
2. **RAM-sized node, so the pod gets most of the swap.** CPU is requested off the
   RAM request (below), so it never inflates the node beyond what RAM needs. The
   request is therefore a large fraction of node RAM (~74% for a 13k job on a
   256Gi node), and `LimitedSwap` grants swap in that proportion, so the pod
   receives most of the 2x swap.
3. **Limit margin.** The limit is `peak * 1.2`, 20% above the fitted peak, which
   tracks observed peaks closely (144 observed vs 142 predicted at 3000 images).

**The caveat to watch:** `LimitedSwap` grants swap *proportionally*, not as
`limit - request`:

```
pod swap allowance = (memory request / node RAM) * node total swap
```

This is why keeping the node RAM close to the request matters (buffer 2): if CPU
or a large instance inflated the node, the request would be a small fraction of
it and the pod would get too little swap. Driving selection by RAM avoids that.

If outliers appear, the levers in order are: lower `SWAP_RATIO` (a larger request
means both more scheduled RAM and a bigger swap share), then more node swap.
Raising only `MARGIN_PERCENT` has little effect once the proportional swap share
is the binding constraint. `SWAP_RATIO` defaults to 0 (off, safe); production
sets `1.0` alongside the swap pool (see the amendment below). Validate on a real
large job. The per-workflow burst-headroom annotation (= limit - request; not the
actual LimitedSwap grant) plus node swap metrics (`node_memory_Swap*`, and
`container_swap_limit_bytes` for the real per-pod allowance) are the backstop.

### Amendment (2026-07-30): prod ratio lowered 2.0 → 1.0

The benchmarked `2.0` (request = peak/3) was too aggressive on a real job. A
1233-image run was **evicted for node memory pressure** - a node-level eviction
(graceful TERM, node `available: 408Ki`), not a cgroup OOM-kill - during OpenMVS
depth-map fusion:

- Predicted peak ≈ 67.8Gi → request 22.6Gi (`23138Mi`), limit ≈ 81Gi.
- Resident set at eviction: **28.2Gi (~42% of peak)**, and still climbing (fusion
  only 10.6% done; mvs-texturing not yet reached).

Buffer #1's premise - that ~1/3 of the peak is resident and the rest is cold
enough to spill to swap - does not hold at the fusion stage: those pages are hot,
so the kernel can't page them out, and the resident set alone exceeded the node's
physical RAM (Karpenter sizes the node off the RAM *request*). Swap only rescues
cold pages.

Moving to `1.0` (request = peak/2) sizes the node's physical RAM above the
observed resident fraction and, per the proportional-swap formula, still grants a
large swap share for the genuinely brief texturing spike. It gives up some of the
RAM-cost saving in exchange for not under-sizing physical RAM. If a future job's
resident set exceeds half the peak, lower `SWAP_RATIO` further before touching
`MARGIN_PERCENT`.

## Consequences

- Nodes are provisioned for the resident set, not the peak, cutting RAM cost and
  raising the images-per-machine ceiling substantially.
- The estimate extrapolates beyond the 5000-image table (last-segment slope,
  ~0.043 GiB/image) instead of clamping, so large jobs are sized realistically.
  `MEMORY_MAX_GIB` bounds it to what the pool can schedule. At the `1.0` ratio
  (request = peak/2) the ceiling for a 256Gi r-family NVMe node (e.g. r6id.8xlarge
  + 2x swap) is ~8-9k images (peak ~380Gi, ~190Gi RAM request); at the old `2.0`
  it was ~13-14k. The lower ratio trades some images-per-machine headroom for not
  under-sizing physical RAM. Beyond the ceiling needs bigger-RAM instances, out of
  scope for this pool.
- Nodes **must** provide swap. Without it, a Burstable pod that exceeds its
  request is OOM-killed at the peak. Enforced on AWS by the swap-enabled
  EC2NodeClass; on other clusters it is an operator responsibility (docs/swap.md).
- On AWS, ScaleODM runs on a dedicated tainted pool (`pool=scaleodm`) so the
  NVMe/swap nodes are isolated from other workloads and one big job can't starve
  the shared pool's capacity. See docs/swap.md.
- Peak-time performance degrades while swapping (disk is slower than RAM), but on
  AWS the swap is on local NVMe instance store (`*id` families), ~100x faster
  than EBS, so heavy paging stays acceptable.
- Effective OOM headroom depends on the proportional swap formula above, so
  `SWAP_RATIO` should be validated per real workload rather than trusted blindly.
- `SWAP_RATIO=0` restores the old behaviour (request the full peak as RAM) for
  clusters without swap.
- A job that gets OOM-killed mid-run but reports success is not necessarily fine:
  OpenMVS surviving an OOM may mean a subprocess or optional stage was skipped.
  Validation must check expected outputs (orthophoto, DSM, point cloud) and
  kernel OOM counters (`dmesg` / `node_vmstat_oom_kill`), not just the workflow's
  final status.

### CPU sizing

Node selection is driven by RAM. CPU is requested per GiB of the RAM *request*
at the r-family ratio (`CPU_PER_GIB=0.125`, 1 vCPU per 8Gi), so the CPU request
always fits the RAM-selected r-node and never forces a bigger instance.

In production the CPU *limit* is omitted (`CPU_LIMIT_MULTIPLIER=0`), so ODM
bursts to every core on the node (ODM defaults its concurrency to all detected
CPUs; we pass no `--max-concurrency` flag). The generic chart default keeps
`CPU_LIMIT_MULTIPLIER=1.5` (a bounded limit) as the safe out-of-the-box value;
set it to 0 to allow bursting. CPU therefore affects only speed, never
feasibility, and a `--split` submodel workflow is not needed for scheduling (it
remains a possible future wall-clock optimisation).

### Spot vs on-demand

Jobs at or above `ONDEMAND_IMAGE_THRESHOLD` (5000) are auto-upgraded from spot to
on-demand, because they run for hours and a spot eviction would waste the whole
run. Smaller jobs stay on cheap spot. An explicit on-demand request is always
honoured.
